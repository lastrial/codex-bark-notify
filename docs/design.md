# 设计说明

## 目标

主聊天每轮回复结束时发送 Bark；异步问题卡片被应用接受时单独提醒。通知标题为执行主机名，正文为准确的聊天名称加状态。完成使用 `calypso`，等待回答使用 `alarm`。

Skill 负责管理，事件处理由独立脚本执行，不要求模型在每轮结束前主动调用发送工具。

## 组成

| 文件 | 职责 |
| --- | --- |
| `manage.py` | 完成通知安装、启停、状态及已知完成事件测试 |
| `notify.py` | 保留原回调、筛选结束事件、持久去重与有界发送 |
| `read_thread_title.py` | 通过 Codex app-server 查询聊天元数据 |
| `manage_questions.py` | 管理自有 PostToolUse 配置，保留其他 Hook |
| `question.py` | 筛选成功异步提问并独立去重，复用发送设施 |

## 事件与身份

完成入口只接受 `agent-turn-complete`，要求规范的线程和轮次 UUID。读取元数据后，只允许已知主聊天来源及真实非空名称。子代理、未知来源或名称不可得时跳过，不根据预览文字猜测标题。

提问入口要求 `PostToolUse`、准确工具名 `request_user_input_async` 和布尔 `accepted: true`。响应可以是 JSON 字符串或对象。存在 `agent_id` / `agent_type` 即跳过；transcript 文件名末尾 UUID 必须与会话 ID 一致。只检查路径，不打开 transcript。

实际子代理 Hook 可能使用父聊天的 session ID，因此不能只依靠 session ID 查询标题来判断主聊天。

## 去重与结果

完成键为主机 ID、聊天 ID、轮次 ID；提问键另加工具调用 ID。两类事件使用独立 SQLite 数据库，在元数据查询和网络请求前取得一次处理资格。

结果包括 `processing`、`sent`、`rejected`、`unknown`、`skipped`。HTTP 200 且业务码为整数 200 才记录 sent；不确定响应或超时记录 unknown。遗留 processing 超时后转 unknown。所有已存在记录都不自动重试。

这个策略避免网络结果不明时重复提醒，但可能漏掉未实际送达的通知。首版没有补发队列。

## 执行与停用

事件入口尽快启动独立 worker 并退出。提问 Hook 静默返回 0，失败不会阻止问题工具。后台参数只传身份和路径；查询与网络请求有总预算，结束时清理子进程。

完成包装器通过 exec 原样转交原 notify 参数，并保留退出和信号行为。两种发送共用锁；停用取得锁、关闭激活标志后返回。提问发送同时要求主通知和提问通知激活。

配置修改只处理本功能拥有的条目，检测到其他工具改动时保留外部内容并报告冲突。停用和再次启用均保留去重数据库。

## 数据与配置

运行目录权限为 0700，状态和配置文件为 0600。密钥从用户指定的私有文件读取，配置只保存路径；不在 argv、源码或日志中写入密钥。状态仅保存身份、时间和固定结果码，不保存标题、问题或聊天内容。

发送目标固定为官方 Bark 服务的 HTTPS `/push`。该项目尚无自建 Bark 服务地址配置。

非托管 Hook 需要通过 Codex 原生 `/hooks` 信任。安装器不修改信任记录，不启用全局绕过。
